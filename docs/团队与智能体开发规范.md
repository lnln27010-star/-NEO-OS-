# NEO-OS 团队与智能体开发规范（v1）

适用范围：四位同学、他们使用的编码智能体，以及之后加入的开发者。目标是让各中心能并行开发，仍共用同一套界面、数据和计算口径。本规范以仓库当前可运行代码为起点；尚未接入的技术不写成“已经具备”。

## 1. 统一技术选型

| 层 | 统一方案 | 约束 |
| --- | --- | --- |
| 前端 | React 19 + TypeScript（`strict`）+ Vite 8 | 业务页面用 `.tsx`；新增逻辑不写 JavaScript，不引入第二套前端框架。|
| 状态 | Zustand 5；组件局部状态用 React state | 跨页面状态按业务域建 store；服务端数据不得只保存在浏览器 store 中。|
| 2D / 3D | 现有高德地图接入、MapLibre、Three.js、React Three Fiber | 共用已有场景加载与视角状态；新页面不再各建一套地图库或渲染器。|
| 图标 | `lucide-react` | 不混用 emoji、图标字体和另一套图标包。|
| 样式与组件 | 项目内 `src/styles.css`、业务样式文件及共享 `src/components/ui/` | 当前项目**没有** Ant Design/shadcn/ui/Tailwind 的完整组件体系。先提取和复用现有按钮、输入框、卡片、表格等样式；复杂无障碍交互统一用经团队评审的 Radix UI 原语封装，业务页不可直接带入另一整套视觉样式。|
| 后端 | Python 3.12 + FastAPI + Pydantic v2 | API 保持 `/api/platform/*`（业务）与 `/api/simulation/*`（求解）边界。|
| 存储 | SQLite + 现有 Repository，数据放 `.solver-data/` | 原型和单机协作阶段沿用现状。多人同时写入、正式部署时先设计 PostgreSQL 迁移方案，再实施；不能只改连接串。|
| 工程计算 | pandapower、PyPSA/HiGHS；OpenFOAM、FEniCSx 经现有适配器与容器运行 | 算法、版本、输入快照和结果必须可追溯。|
| 依赖安装 | `package-lock.json`、`backend/requirements.lock.txt` | 锁文件跟随依赖变更一同提交。|

不为“统一”立即重写旧模块。新功能遵守本规范，旧页面在触及或重构时逐步收敛。

## 2. 四人分工与集成边界

每人负责一个**纵向业务域**：页面、接口、数据模型、测试和说明都在其职责内。下表的“同学 A～D”是分工槽位，确定人选后在项目看板填实际负责人。

| 负责人 | 主责 | 主要代码范围 | 交付的最小闭环 |
| --- | --- | --- | --- |
| A：全域孪生与统一体验 | 全域驾驶舱、全球能源网、园区/机房、主题与共享组件 | `src/scene/`、场景相关 `src/components/`、`src/useDesignerStore.ts`、`src/components/ui/` | 场景可进入、可交互、深浅主题一致，场景失败可恢复。|
| B：规划选址与投资 | 全国机会地图、证据、项目机会池、选址尽调、IDC 测算 | `src/components/NationalOpportunity*`、`PlanningWorkbench*`、`src/idcInvestment.ts`、`backend/planning_*` | 从地区/园区候选到项目档案、测算和结果复核可走通。|
| C：设计工程与求解 | 供电/冷却拓扑、设计版本、四引擎求解、结果展示 | `src/engineeringSimulation.ts`、工程/仿真组件、`backend/engines/`、`backend/jobs.py`、`backend/worker.py` | 用一份可追溯的输入得到真实结果或明确不可用原因。|
| D：基础信息与运营接入 | 数据中心资料、设备/图纸/测点、协同运营、智能运维 | `src/components/Foundation*`、运营组件、`backend/foundation.py`、`operations.py`、`documents.py`、`work_orders.py` | 资料维护、发布、变更、测点/工单有明确状态与审计记录。|

每周指定一名**集成负责人**（轮值，名字记在项目看板），负责公共文件和跨域接口的最终合并，不代替代码评审。以下文件是集成敏感区：`src/App.tsx`、`src/components/CenterWorkspace.tsx`、`src/styles.css`、`src/usePortalStore.ts`、`backend/api.py`、`backend/models.py`、`package.json`、`backend/requirements*.txt`。改动前在 Issue/PR 说明拟改的入口、数据契约和受影响模块；由集成负责人协调，避免四个分支同时重排同一个大文件。

新增中心入口时先在自己的模块实现可独立加载的页面，再以小改动接入共享导航。不要把整页业务实现继续塞进 `CenterWorkspace.tsx` 或 `backend/api.py`；后续重构路由应保持已有 API 路径兼容。

## 3. 前端与视觉规则

1. **主题来源**：深浅主题与地图底图状态见 `src/useVisualTheme.ts`。颜色、背景、字体和基础按钮以 `src/styles.css` 的实际变量和现有页面为准；`design-system/computepowertwin/MASTER.md` 是历史草案，与实际界面冲突时以当前运行样式为准。
2. **共享组件**：重复两次以上的按钮、筛选器、字段行、状态标签、空状态、加载态，提取到 `src/components/ui/`，提供统一 props、键盘/焦点行为和主题样式。简单元素优先原生语义 HTML；模态框、菜单、弹出层等复杂交互需要无障碍基础时，用同一套 Radix UI 原语封装后再供业务使用。引入前先完成依赖评审与锁文件更新。
3. **图表与地图**：不要将省级平均电价画成具体项目的到户电价；图例要标单位、月份、来源和缺数状态。地图坐标必须标注 WGS84/GCJ02，转换逻辑集中复用，不能静默混用。
4. **性能**：继续按中心和场景懒加载；不要在首页同步引入大型 3D、BIM、XLSX 或求解资源。地图/机房切换显示加载与错误状态，避免整屏白屏。
5. **文案**：面向用户写业务动作和结论，减少解释性口号；关键限制（如“参考数据”“未核实”“引擎不可用”）必须保留。深浅两套主题和典型桌面宽度都要检查。
6. **网络调用**：新增业务域优先建立同域 API 模块，统一处理超时、HTTP 错误和返回类型；不要在 JSX 中散落裸 `fetch` 和 `any`。迁移旧调用时按功能逐步进行。

## 4. 后端、接口与数据库规则

- 请求/响应使用 Pydantic 明确字段、范围、枚举和单位；前端 TypeScript 类型与 API 契约在**同一 PR** 更新。不要仅靠前端校验。
- URL 用名词与资源层级，读取 `GET`、创建 `POST`、更新 `PUT/PATCH`；失败返回明确 HTTP 状态和可读错误。对外接口不要直接泄露 Python 异常栈。
- 写入涉及版本的档案继续使用 `expected_revision` / 修订号，冲突要显式报告，不能覆盖他人的新版本；需要变更历史的数据保留审计信息。
- SQLite schema 变更必须有可重复执行、向前兼容的迁移步骤或明确版本升级脚本，并用旧库副本验证。不能手工改自己的 `.solver-data/*.sqlite3` 后以为团队库也会自动变化。
- 数据库内存 ID、文件路径、上传文件名等都经后端校验；上传限制大小与类型，不将任意路径拼进文件读写。密钥只放本地环境变量或密钥管理，不能写入前端源码、日志、PR 或示例数据。
- 本地 `127.0.0.1` 服务、SQLite 和当前鉴权状态只是开发基线；要对公网开放时需单独完成账户权限、审计、备份、迁移与安全审查。

## 5. 业务数据和计算口径

每项用于筛选、投资决策或仿真的输入都要能追溯：`source`、`observed_at` 或适用月份、单位、地理范围、数据状态（实测/已核实/引用/假设/缺失）、录入人或证据引用。日期用 ISO 8601，后端存 UTC；界面按业务场景展示当地时间。

统一单位优先采用：功率 kW/MW，电量 kWh，电价元/kWh，温度 °C，水量 m³/h 或 m³/日，长度 m，时延 ms，金额在接口字段名明确 `yuan`/`wan`。变换单位必须写在转换函数或类型名中。禁止同一个 `price` 字段同时表示代理购电价、到户价和项目假设价。

分析结果须附输入版本、模型版本、求解器/运行环境、时间与状态：

- **正式计算**：记录真实求解器、输入快照、成功/失败日志和输出；引擎缺失就显示不可用。
- **情景估算**：展示公式、参数和假设，不能标成潮流/CFD/有限元“实算”。
- **公开地区数据**：只用于全国初筛；进入具体场址前要求接入、电价、客户、土地、水、网络等项目级证据。
- **机房模型**：程序化模型与厂商 BIM、现场设备/测点明确区分；设备连接关系是计算输入，图上画一条线不等于真实接线。

## 6. Git、任务和评审

1. `main` 只放已审查且可构建的代码。每个任务从最新 `main` 建分支，建议 `feature/<业务域>-<任务>`、`fix/<业务域>-<问题>`；一个 PR 只解决一个可验收问题。
2. 任务描述至少包括：业务场景、用户动作、输入与来源、预期输出、缺数/失败表现、验收示例、归属同学。跨域任务先明确接口负责人。
3. PR 必填：变更摘要、影响页面/API/表、数据口径、测试命令及结果、界面截图（有 UI 改动时）、迁移/回退说明（有数据结构改动时）。作者先自查，再由另一位同学评审；公共文件由集成负责人复核。
4. 不提交 `.env*`、`.solver-data/`、`node_modules/`、`.venv-sim/`、`dist/`、日志、真实客户资料和未经授权的图纸/模型。GitHub 仓库是公开的，演示截图也要检查是否含敏感数据。
5. 不用一次全局格式化掩盖功能改动。新文件使用 UTF-8、LF、末尾换行；`.editorconfig` 是新增文件的基本格式约定。已有文件按触及范围逐步整理。

**PR 描述模板**

```md
## 业务目标
<!-- 谁在什么场景做什么 -->
## 改动范围
<!-- 页面 / API / 数据库 / 求解器 -->
## 数据与计算口径
<!-- 来源、月份、单位、假设、缺失处理 -->
## 验证
<!-- 命令、结果、关键交互截图 -->
## 风险与回退
<!-- 兼容性、迁移、尚未接入的能力 -->
```

## 7. 本地运行与最小验收

```powershell
npm ci
npx tsc -b --pretty false
npm run build
```

需要后端/仿真时，先运行 `scripts/setup-simulation.ps1` 创建 Python 3.12 环境，再运行 `scripts/start-platform.ps1`。前端开发用 `npm run dev`；代理目标为本机后端 8001。脚本和端口以仓库配置为准，不自行改成各人不同端口后提交。

按改动范围运行现有脚本和 Python 单测，例如：

```powershell
node scripts/test-national-ranking.mjs
node scripts/test-idc-investment.mjs
.venv-sim/Scripts/python.exe -m unittest discover -s backend/tests -p 'test_*.py'
```

新增业务规则要有能失败的测试；界面改动至少人工核对主路径、空数据、接口失败、深浅主题和返回导航。验收不以“页面能打开”为唯一标准，需从输入走到保存/求解/结果，并核对数值与来源。

## 8. 给编码智能体的任务提示骨架

```text
先读根目录 AGENTS.md 和 docs/团队与智能体开发规范.md。
业务域：[A/B/C/D]，任务：[具体目标]。
可改范围：[文件/模块]；如需改公共文件，先说明接口与合并影响。
输入及来源：[数据/版本/单位]；输出与验收：[用户操作和可核对结果]。
保留现有真实/假设/缺数状态，不伪造求解或现场数据。
完成后运行相关测试，报告变更、验证结果和剩余限制。
```

当团队决定更换数据库、组件体系或地图/求解方案时，先提交一页技术决策记录：为什么换、迁移成本、与当前功能的兼容方式、回退路径；评审通过再编码。
